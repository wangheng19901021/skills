# 需求评审规则

在生成任何业务接口代码之前，必须先向用户确认以下三点。
如果用户未明确说明，必须主动追问，不得直接假设默认值。

## 1. 并发模型
- 同一时刻可能有多少请求访问同一份数据？
- 期望的处理方式：幂等 / 行锁 / 乐观锁 / Redis 预扣？
- 典型案例：C 端用户连点 → 优先幂等；B 端批量发放 → 行锁保底

## 2. 上游输入
- 每个字段的来源是谁？（HTTP 请求 / MQ / RPC / 内部计算）
- 哪些字段可能为 null 或空字符串？
- 必填字段用 Bean Validation，非必填字段用 Optional

## 3. 失败语义
- 操作失败要不要回滚？回滚到哪个边界？
- 流水、日志、通知算不算回滚范围？
- 外部通知类操作必须独立于数据库事务生命周期

## 规则清单（6 条）
- R1-1 生成接口代码前必须确认并发模型：同一时刻多少请求碰同一份数据、期望幂等 / 行锁 / 乐观锁 / Redis 预扣（推演）
- R1-2 用户未说明并发模型时必须主动追问，禁止假设默认值（推演）
- R1-3 逐字段确认上游来源（HTTP / MQ / RPC / 内部计算）及可空语义（推演）
- R1-4 必填字段用 Bean Validation，非必填字段用 Optional 或显式默认值（推演）
- R1-5 确认失败语义：要不要回滚、回滚到哪个边界、流水 / 日志 / 通知算不算回滚范围（推演）
- R1-6 影响半径不可审计、不可回收的需求（如"超级管理员切换租户身份"），先问"这个功能最坏会怎样"，再决定做不做（炸出——被人凭直觉拦下的真实需求）
